### Per-user Microsoft Graph isolation (commit `c96129d`)

The Microsoft Graph integration (shipped April 6) used `getValidToken()` with no user scoping. With one user this was invisible. With two users — the prerequisite for opening Instinct to the team — Bob would have seen Alice's calendar and email in his briefing. **This was a real privacy bug.**

Fixed it end-to-end:
- Every layer scopes by `connected_by`: `getValidToken(userId)`, `getConnectionStatus(userId)`, `deleteTokens(userId)`, all 6 `fetchLive*` helpers, all 6 public `fetch*` wrappers
- In-memory cache keys namespaced by userId; `clearCache(userId)` only clears that namespace
- `graphFetch` records the real userId on `microsoft.api_called` events instead of literal `"system"`
- New events: `microsoft.token_refresh_failed`, `microsoft.fetch_failed`
- OAuth callback verifies an HMAC-signed `state` parameter (`signState`/`verifyState`) instead of trusting the session cookie. Forged or mismatched state → 400.
- Migration 006 drops the unique index on `user_email`, adds a unique index on `connected_by`, cleans up orphan rows from the old single-tenant assumption.
- 6 new isolation tests in `microsoft-graph.test.ts`.
- **Critical: QuickBooks was deliberately NOT changed.** It's single-tenant by design (only the CEO connects company books). Don't let symmetry tempt you into a "consistency refactor."
- Migration 006 applied to production.

### Plaud meeting transcript ingestion (commits `fe2a49a`, `85f0bd5`)

The biggest feature shipped today. Plaud is the AI voice recorder the executive team uses. Transcripts were trapped in Plaud's app. We pulled them into Instinct's shared knowledge base so the Wolfpack Assistant can answer "what did Hoxsie commit to in Tuesday's call?"

Architecture (verified against Plaud's official docs at `docs.plaud.ai`):
- **Webhook-driven** (Plaud's recommended method)
- Endpoint: `POST /api/integrations/plaud/webhook`
- Auth: HMAC-SHA256 in `Plaud-Signature` header, verified against `PLAUD_WEBHOOK_SECRET`. Verification runs against the **raw request body** (`req.text()` not `req.json()`) — JSON whitespace re-serialization breaks HMAC. Timing-safe comparison.
- **Org-level scope** (one shared API key for the team) — Nick chose this because the team is small (5) and meeting context benefits everyone. `owner_user_id` is still recorded on every transcript so we can switch to per-user retrieval later without re-ingesting.
- **Idempotent**: unique index on `file_id`. Plaud may re-deliver. Re-delivery returns `status: "duplicate"`.
- **Doc quality gate runs first**: PII/security/compliance check before any storage.
- **Triple-write**: PG (system of record) + Qdrant (semantic search) + analytics events.
- **Per-user analytics**: every event attributed to the resolved owner, never `"system"`.

UI surface in commit `85f0bd5`:
- Settings → "Plaud — Meeting Transcripts" tile
- New `/meetings` sidebar page (org-shared list, click-to-expand, lazy detail load)
- **New Wolfpack Assistant Priority 3 retrieval** in `assistant.ts`: cheap keyword gate ("meeting", "discussed", "decided", "follow-up" etc.) → ranked ILIKE search across title (3×), summary (2×), body (1×) → returns top 3 with snippets. Logs `source="meeting_transcripts"` and fires `system.ai_call_skipped` with `reason="meeting_transcripts_hit"`.

24 tests in `plaud.test.ts`. Migrations 007 (Plaud schema + learning view) and 008 (allow `meeting_transcripts` as `apex_messages.source`) applied to production.

**The correct architecture I landed on:**
The AgenticQA repo also has a **FastAPI orchestrator** at `agent_api.py` with 50+ endpoints. The right consumer pattern (and the one AgenticQA was built for) is: run the FastAPI server, POST to `/api/workflows/requests`, auto-approve + queue + run worker, poll until complete.

**The infrastructure question:** I initially looked at `railway.toml` + `Dockerfile` and assumed there was a live Railway deploy. Probed `agenticqa-production.up.railway.app` — got 502. Then Nick said he didn't remember setting up Railway. **It was a phantom** — committed by a prior session that never finished. Pivoted to:

**The actual architecture now in place: AgenticQA runs as an in-CI sidecar.**
1. CI clones `nhomyk/AgenticQA` into `agenticqa-src/` using a PAT (`AGENTICQA_REPO_PAT`)
2. `pip install -e .` from the `agenticqa-src/AgenticQA/` subdirectory (the python project lives in a subdir, not at repo root — the root has the JS agents + Dockerfile)
3. Boots `python -m uvicorn agent_api:app` on `127.0.0.1:8765`
4. Waits for `/health` → 200
5. POSTs `/api/workflows/requests` with `repo=$GITHUB_WORKSPACE` (the worker resolves `repo` as a local filesystem path, not a clone URL)
6. Auto-approves, queues, runs worker
7. Polls `/api/workflows/requests/{id}/status` until terminal
8. Renders results in step summary
9. Always-runs cleanup kills the sidecar pid

**Bug found and fixed in AgenticQA itself (commit `a84d9f0` in `nhomyk/AgenticQA`):**
The first end-to-end run failed with `invalid_transition:IN_PROGRESS->IN_PROGRESS`. Root cause: a race between the background `WorkerPool` (which calls `atomic_pickup`) and the explicit `/api/workflows/worker/run/{id}` path (which calls `run_request` directly). The background pool wins the DB transition, then the explicit caller's stale in-memory `req["status"]=="QUEUED"` triggers `start_request` which raises because the row is now `IN_PROGRESS`. **Fix: made `start_request` idempotent.**

**What the final run actually did (run `24106176630`):**

- ✅ Queued → `QUEUED`
- ✅ Picked up by background worker `w_728ec701` → `IN_PROGRESS`
- ✅ Created feature branch `agenticqa/wr_ed7b9958d143-run-full-pipeline-against-this-r`
